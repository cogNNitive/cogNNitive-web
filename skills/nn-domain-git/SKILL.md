## Role

Gated workspace-to-Git review workflow: initialize a private repo with an opinionated
`.gitignore`, work branch-per-change behind `validate`/`check_workspace` PR gates,
track the two-layer version map (`V_x-y-z` vs Git commit), and keep a timestamped
filesystem backup outside the workspace before deep changes.

## Workflow

### Step 1 — Prerequisite Check (Abort With Zero Side Effects)

Run before anything else:

```bash
git --version
git ls-remote <remote-url> HEAD
```

If Git is missing or authentication fails, abort immediately:

```markdown
⛔ Git or remote authentication is unavailable. Aborting with zero side effects —
no repo created, no branch cut, no remote touched.
```

Do NOT create repos, branches, commits, or remotes on this path.

### Step 2 — Menu

Present exactly:

```markdown
Workspace-to-Git workflow:
[a] init — private repo + opinionated .gitignore
[b] branch + PR — branch-per-change with validate + check_workspace gates
[c] map — record V_x-y-z ↔ commit rows
[d] backup — timestamped filesystem copy outside the workspace
```

Wait for the choice. Do NOT proceed on ambiguity.

### Step 3a — Init (Private by Default + Opinionated .gitignore)

1. Create the remote repository as **private**. If the host defaults to public,
   stop and require the user to flip visibility to private first.
2. Write this `.gitignore` at the workspace root:

```gitignore
# Workspace review layer — generated by /nn-domain-git
staging/
original/
specs/
*.env
*.token
*.pem
*.key
secrets/
```

`staging/` holds scratch review output. Heavy `original/` inputs stay local.
Generated `specs/` cache output is not reviewed. Secrets (`*.env`, tokens, keys)
are never tracked.

3. Confirm with `git status`: ignored paths MUST NOT appear as staged.

### Step 3b — Branch per Change + Gated PR

1. Cut one branch per change from a clean `main`:

```bash
git checkout -b <change>/<short-slug>
```

2. Commit with conventional commits. Push the branch only after double confirmation
   (see Double-Confirm Rule below).
3. Open a pull request targeting `main`. The PR MUST pass BOTH gates before merge:

- `validate` (model validation via `innfo-mcp_validate_model`)
- `check_workspace` (workspace integrity check)

4. `main` MUST be protected and MUST require at least 1 approval. A PR missing
   any gate result or approval is blocked — never merge it, never force-push over it.

### Step 3c — Two-Layer Version Map

`V_x-y-z` model versions are the system of record. Git commits are a separate
review layer. A version NEVER equals a commit. Maintain the map explicitly:

| Model version | Git commit | Date |
|---------------|------------|------|
| V_0-2-0 | <sha> | <date> |

Example row:

| V_0-2-0 | `a1b2c3d` | 2026-09-09 |

Record one row per released version. When the map is consulted for a version,
return the corresponding commit AND restate that the version is not the commit.

### Step 3d — Timestamped Offline Backup

Before any deep change, write a timestamped filesystem copy OUTSIDE the workspace:

```bash
node scripts/backup-workspace.js --workspace-dir <dir>
```

If the automated backup fails, use the manual fallback: copy the whole workspace
folder to a backups directory on disk (e.g. `xcopy /E /I <dir> <dir>-backup-<timestamp>`
on Windows), and confirm it exists before continuing.

The backup MUST exist with an earlier timestamp than the first mutation.
Never rely on Git alone for recovery.

## Double-Confirm Rule

Remote or destructive operations (push, merge, force operations, visibility changes,
history rewrites) REQUIRE two explicit confirmations. After the first confirmation,
restate the exact operation, target, and irreversibility, then ask again. If only
one confirmation is given, the operation MUST NOT execute.
